## 2. 问题清单

### F01 / P1：当前源码不能通过 Rust 编译（实测）

- 位置：`src-tauri/src/extractors/text.rs:22,65,94,166`，`extractors/limits.rs:93`。
- `text.rs` 导入不存在的 `GARBLED_REPLACEMENT_PERMILLE`，实际定义为 `GARBLED_MARK_PERMILLE`；`DecodedText` 已定义 `suspicious`，构造、读取和测试仍使用 `replacements`。
- 实测报 E0432、E0560、E0609；library 6 个错误，library test 10 个错误。全量测试未进入执行阶段。
- 修复方向：统一乱码判定字段及常量语义，再运行文本解析测试和全部旧阶段回归。不要为了让 T09 测试通过而静默删除用户正在开发的 T10 模块。

### F02 / P1：历史列表必然被前端契约校验拒绝（实测复现）

- 位置：`src/api/client.ts:209,214` 及 `decodeResponse`；`src-tauri/src/commands_execute.rs:266`、`commands_recovery.rs` 的 `recover_pending_runs`。
- 后端 `list_runs` 返回 `Vec<RunReport>`，前端映射却为 `null`；`decodeResponse` 将该分支统一解释为“非空字符串 taskId”，连合法的空历史 `[]` 也拒绝。历史页因此无法正常加载，间接阻断撤销和恢复入口。
- `recover_pending_runs` 返回 `Vec<RecoveryReport>`，前端却按 `RecoveryStatus` 对象校验，同样不匹配。目前 UI 未接入该命令，但接入就会失败。
- 通过 Vite SSR 加载实际 `client.ts`，分别调用 `decodeResponse(command, {ok:true,data:[]})`，两者都得到 `IPC_TRANSPORT_FAILED / 本地核心返回的数据不符合应用契约，已拒绝使用`。
- 修复方向：显式区分标量、对象、数组及 nullable 响应，对数组逐项校验；添加不 mock `call/decodeResponse` 的契约接线测试。

### F03 / P1：重启后重新选择同一目录，仍不能授权旧历史（静态确认）

- 位置：`safety/root.rs:198`；`commands.rs::choose_root`；`app_state.rs:159–174`；`commands_undo.rs:132`；`commands_recovery.rs::authorized_root`；`recovery/startup.rs::root_for_run`。
- 每次 `approve_root` 都生成新 UUID，`choose_root` 插入新根并以新 ID 注册内存授权。旧计划仍引用旧 `rootId`，所有恢复/撤销命令却只用旧 ID 查内存表，没有按真实路径、卷身份、根文件身份复核并重新绑定的流程。
- 触发：整理后退出，重开并选择原目录，再撤销旧记录；旧根仍返回 `ROOT_NOT_AUTHORIZED`。崩溃恢复也会一直等待一个现有 UI 无法重新登记的旧 ID。
- 修复方向：提供后端受控的历史根重新授权；原生选择后验证路径、卷、根身份，匹配成功才绑定历史 ID。不能只比路径或自动沿用旧授权。
- 验收：用新的 AppState/会话重开同一测试 DB，重新授权后可撤销/恢复；同路径被替换的目录必须拒绝。

### F04 / P1：撤销目录清理存在身份检查与删除之间的竞争窗口（静态风险确认，未做竞态注入）

- 位置：`executor/undo.rs:621–686`；`platform/windows.rs:231`。
- `clean_created_dirs` 用普通 `open_directory` 取身份，句柄在闭包返回后释放，随后按路径 `remove_dir`。该打开函数还允许共享 DELETE，未逐级保护祖先，未拒绝重解析点。
- 触发：身份核验后、删除前，外部进程移走原分类目录并创建同名空目录。程序可能删除后来创建的用户目录，而非日志记录的那个目录；祖先被换成联接点也缺少对应保护。
- 非递归删除确实防止递归清空文件，但不能保证“只删除本任务创建的目录”。
- 修复方向：受保护的根/祖先链、重解析点拒绝、目标目录身份绑定和安全句柄式删除；清理前后记录可恢复的审计状态。不要简单保留一个禁止删除共享的句柄后仍调用路径删除，需验证 Windows 删除语义。
- 验收：TempDir 中在检查/删除之间设置 barrier，替换目录及祖先；新目录、根外目录均不得被删除。

### F05 / P1：撤销只检查自己的原 run，绕过全局恢复阻塞（静态确认）

- 位置：`executor/undo.rs:478` 的 `ensure_not_blocked`，对照 `storage/execution.rs::admit`。
- 撤销仅检查 `original_run_id` 的 `recoveryRequired` 和 ambiguous 项；另一个 run 的未决 prepared/ambiguous 或 recoveryRequired 不参与检查。进程执行锁释放后，有未决任务仍能对另一条历史开始撤销，违反规格 §8.2 的全应用阻塞规则。
- 修复方向：正向执行和撤销复用全局持久阻塞查询，在获得执行锁后、消费确认及创建 run 的事务内检查；acknowledged 的处理保持统一。
- 验收：A 留下未解决恢复记录，B 的撤销必须被拒且不消费 token；A 确认处置后才能放行。

### F06 / P1：撤销 requestId 重试不返回已有结果，且入场不是一个事务（静态确认，现有测试错误固化）

- 位置：`executor/undo.rs:169,229`；`storage/runs.rs:695`；`tests/undo_windows.rs:627`。
- 先消费 undo token，远后于此才调用 `journal.begin` 查 requestId。完全相同请求第一次成功、第二次重试会返回 `TOKEN_USED`，到不了返回已有 run 的分支。现有 `the_same_request_id_undoes_only_once` 正在断言这个错误行为；它证明“不重复移动”，没有证明幂等响应。
- 消费令牌、全局检查、建 run 也是分开的事务，途中失败可能消耗确认而不留下对应 run。`Journal::begin` 只绑定 planId/direction，不能完整区分 undoPlanId、原 run、摘要、token 与选择集合。
- 修复方向：先按 requestId 查已登记的完整参数绑定，再取锁；在事务中完成准入和消费。相同请求返回同一 run，不同参数返回 REQUEST_CONFLICT；另一个 requestId 重用 token 才应返回 TOKEN_USED。
- 验收：响应丢失后重试、重复点击、同 ID 不同选中集合、事务插入失败回滚、TASK_BUSY 不消费确认。

### F07 / P1：普通撤销失败没有关闭反向操作状态，仍继续后续移动（静态确认）

- 位置：`executor/undo.rs:293–380`；`storage/runs.rs::commit_undo_prepared/mark_undo_conflict`。
- 反向操作先写 prepared。`move_no_replace_with` 返回明确未移动的错误后，只把原操作 `undoStatus` 改为 conflict，没有把本次反向 operation 置 failed，也没有停止循环。
- 触发：预览后目标被占用、源被写锁占用等。run 最后可为 partial，但其中仍留下 open/prepared；正向准入会因此阻塞。多选时后续文件仍可能继续移动，违背首个执行失败停止后续的约定。
- 修复方向：确定未移动则事务写反向 failed、原操作 conflict 和事件，后续项 skipped；不确定则 recoveryRequired 并停止。日志错误出口也需要统一收尾，不能靠下次重启纠正。
- 验收：三个项目中第二项注入移动失败，第三项原位，日志无遗留 prepared；单独覆盖移动后落日志失败。

### F08 / P1：撤销结果被页面接线清掉，恢复异常还可能显示全部成功（静态确认）

- 位置：`UndoPage.tsx:126–128,313`；`App.tsx:152`；`executor/undo.rs:333–360`。
- 成功收到报告后执行 `setResult(report)` 紧接 `onDone()`；App 的 onDone 将 runId 清成 null，组件走“请从历史选择”空态，结果和目录清理警告无法保留给用户查看。
- `recoveryRequired` 分支设置 needs_recovery 后 break，但没有同步冲突/未处理计数；UI 只用 `conflicted === 0 && untouched === 0` 决定“全部完成”，不看 status。修好结果展示后，这个分支会暴露错误成功提示。
- 结果区没有渲染 `result.items`，分项失败原因仍留在后端报告，界面展示的是旧预览项。
- 修复方向：退出由独立按钮触发；按 status 优先展示恢复要求，完整统计剩余未处理项并显示执行结果明细。
- 验收：App 级真实页面接线测试，覆盖正常、部分、recoveryRequired、清理警告；不能只孤立测试 UndoPage。

### F09 / P2：重读撤销报告时原 run ID 和计数不正确（静态确认）

- 位置：`executor/undo.rs:421–468` 的 `report_for_undo_run`。
- `original_run_id` 被填成 `row.plan_id`，计划 ID 不是原执行 ID。
- 只从实际创建的反向 operations 重建列表，预览冲突、未勾选、此前已撤销的项没有对应反向行；重读时 `untouched/already_undone` 固定为 0，warnings 丢失，无法还原首次响应。
- 修复方向：持久保存 undo run 与原 run/undo plan/已确认选中集合的绑定，以及完整结果与清理警告，返回和重读采用同一报告投影。
- 验收：部分撤销后即时响应、get_undo_report、重开 DB 后的报告语义一致。

### F10 / P1：恢复和撤销预览的磁盘读取缺少受保护目录链（静态确认）

- 位置：`executor/undo.rs:803`；`recovery/mod.rs:525`；`safety/root.rs::resolve_within`。
- `resolve_within` 只校验词法组件，之后直接按路径 fingerprint，没有像移动原语那样逐级拒绝/锁住重解析点。祖先替换成同卷联接点时，预览/恢复可能读取批准根之外的文件内容来算哈希。安全移动本身的句柄保护不能倒推预览读取也安全。
- `symlink_metadata(...).is_err()` 又把权限等错误一并当作不存在；恢复判定可能把“读不到”误作“该位置为空”。
- 修复方向：建立受保护的只读快照入口，核验根绑定、祖先链及源身份；仅 NotFound 可表示不存在，其余返回无法判定。恢复与撤销复用安全读取机制而非复制路径读取代码。
- 验收：同卷根外联接、祖先竞争替换、访问被拒、根身份改变，均不得读根外内容或据错误缺失事实放行。

### F11 / P2：撤销没有接入后台任务、进度与取消生命周期（静态确认）

- 位置：`commands_undo.rs:33,55`；对照异步 `commands_execute.rs::execute_plan`。
- 预览哈希和实际撤销都在同步命令内执行；没有为撤销注册 task、发 task-progress 或检查取消。大批量撤销可能长时间占用命令处理，用户无法按已有任务协议停止后续项。
- `lib.rs` 也未注册运行中 CloseRequested 的“停止并退出”处理。不能把崩溃后可恢复当成正常退出和取消已实现。
- 修复方向：复用后台任务服务、全局互斥、观察者和安全点取消；关闭流程等待当前原子操作落日志后退出。
- 验收：三项撤销完成第一项后取消；关闭/重开保留真实已完成项与未派发项。桌面实测而非仅 Web mock。

### F12 / P2：长原路径的撤销兼容性不成立（静态确认）

- 位置：`executor/undo.rs::fingerprint_at/classify`；`safety/fingerprint.rs::move_no_replace_with`。
- 正向移动允许现有源组件超过“新名称 80 UTF-16 units”限制，通过 `resolve_existing_within` 处理。但撤销预览使用 `resolve_within` 读取原路径，反向移动也按新目标规则校验原位置。
- 原文件位于名称超过 80 units 的现有父目录、正向整理到短目录后，撤销可能在读取原位置或目标校验时报 PATH_TOO_LONG。原父目录仍存在也不能恢复。
- 修复方向：区分“用户新建议目标”与“已记录且重新验证的原路径”；不能简单取消所有目标限制。补长原父目录的正向整理→撤销测试。

## 3. 功能缺口与架构不足

### 已到阶段应补齐的接线

- 启动恢复虽然后端执行了标记，但 App 没有调用 recovery_status 并优先展示恢复页；恢复入口依赖历史页，而历史页受 F02 阻断。
- recovery_status / unverified_report 主要按 ambiguous 计阻塞，prepared 或尚无 operation 的 recoveryRequired run 可被显示成无未决项，和正向准入的全库阻塞规则不一致。
- 扫描与执行各自管理任务，begin_execution 只看执行锁，没有统一检查同根扫描占用；App 也没有把全局 busy 状态传给历史/撤销页面。需要后端统一工作流准入，不能仅靠按钮禁用。

### 框架建议（不是要求重写技术栈）

1. 抽出 application service：统一 apply/undo 的准入、幂等参数绑定、恢复闸门、任务取消、错误收尾；目前两套实现明显发生语义漂移。
2. 抽出安全只读/目录清理原语：不能只有 rename 路径严密，而恢复读取和删除路径各自拼接。
3. 将状态与审计事件作为统一事务接口。恢复模块目前先写操作状态、再写事件/原操作 undoStatus；中间失败后重试可能因 applied 跳过补齐。应对每个事务间隙加故障注入。
4. 命令响应形状纳入自动生成或集中声明，测试覆盖实际 decoder。mock 掉 IPC 后页面测试全绿，无法证明 Rust 与 TypeScript 接线正确。
5. 清理误导性注释/ADR：例如把数据库提交描述成“搬回与记 undone 同一个事务”应明确只指两条数据库状态，文件移动不在 SQLite 事务内；旧“分两步写事件”的 ADR 应注明已被替代或尚待统一。
6. `%LOCALAPPDATA%` 缺失时 `lib.rs` 将恢复日志目录回退到 temp，不符合持久恢复记录定位预期。应使用可靠系统应用数据目录或明确停止，不能悄悄降级为临时存储。
