# T04 代码审查与修复报告

## 结论

T04 的主体设计是可靠的：规则模式不联网，规划阶段不改文件，目标名稳定分配，完整指纹在计划可选前绑定，校验摘要包含规格要求的字段，SQLite 写入使用事务与乐观锁。

本次复核新发现 8 类问题，其中 3 类会破坏安全或恢复前提，均已修复并加入回归测试。修复后 Rust 全量 223 条测试、前端 50 条测试全部通过，格式、Clippy、类型检查、Lint、契约差异检查和生产构建通过。

## 已发现并修复

| 级别 | 问题 | 风险 | 修复与证据 |
|---|---|---|---|
| P1 | 已有数据库迁移前没有使用 SQLite Backup API 备份 | WAL 中已提交数据不能靠复制主库可靠保存，迁移故障时缺少规格要求的恢复点 | `Database::open` 仅在已有库确有待执行迁移时创建唯一备份，使用 `rusqlite::backup::Backup`；测试会从 WAL 数据库迁移并打开备份核对原数据 |
| P1 | 校验器没有复核目标扩展名 | T05 编辑或畸形持久化数据可把 `.PDF` 改成 `.txt`，违反 INV-04 | 新增 `EXTENSION_CHANGED` 阻断，扩展名及大小写必须与源文件一致 |
| P1 | 两个选中项可重复引用同一源文件 | 第一项移动后第二项必然失败，且批次语义自相矛盾 | 新增 `DUPLICATE_SOURCE`，同时按 Windows 路径比较键和 `fileId` 检查，所有相关项阻断 |
| P2 | 计划版本只要求“更大”，允许 1→3 跳号；新计划也可从非 1 开始 | revision 不能准确代表每次编辑，削弱旧确认失效与并发冲突判断 | 新计划强制 revision=1；更新强制 `current + 1` |
| P2 | 更新计划可夹带不同的 rootId、scanId、mode、createdAt | 数据库头仍是旧值、计划项却来自另一身份，形成跨根/跨扫描混合计划 | 更新时核对全部不可变身份，不一致返回 `STALE_PLAN`；SQL 不再更新 mode |
| P2 | 旧程序会接受未来版本或有缺口的迁移记录 | 可能按错误 schema 写库并扩大损坏 | 已应用版本必须是当前迁移目录的严格前缀；未来/不一致 schema 返回 `DB_UNAVAILABLE` |
| P2 | 目标目录枚举和重解析点检查吞掉单项 I/O 错误 | 不完整目录事实可能生成错误预览 | 不再使用 `flatten()` / `unwrap_or(false)`；任何不完整观察都明确返回 `PERMISSION_DENIED` |
| P3 | 集成测试把临时根硬编码到用户主目录 | 受限环境全部失败，并可能在用户目录留下测试痕迹 | 改用项目同级 `filepilot-test` 专用基目录，支持 `FILEPILOT_TEST_BASE` 覆盖，单个用例仍由 `TempDir` 自动清理 |

另修复了一个受限环境下的可用性问题：用户直接选择主目录时先按明确路径拒绝并提示“请选择子目录”，不再让 `canonicalize` 的权限错误遮住真正原因；别名/联接仍会在规范化后再次检查，安全边界没有放宽。
