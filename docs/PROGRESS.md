### 打包链路上的一个死锁（本轮最重要的发现）

上一轮我给 `bundle.externalBin` 接上 staging 脚本后，**第一次真跑打包就失败**：

```
resource path `binaries\extract_worker-x86_64-pc-windows-msvc.exe` doesn't exist
[bundle:workers] 编译失败（exit 101）
```

根因不是配置写错，而是**顺序不可能成立**：

| 环节 | 行为 |
|---|---|
| `tauri-build` 的**构建脚本** | 读 `bundle.externalBin`，把列出的文件拷进 target；文件不存在 → 构建脚本直接失败 |
| `extract_worker` | 是**同一个 crate** 的 bin 目标 → 编译它必然触发上面那个构建脚本 |
| staging 脚本 | 恰恰要**先**编译 worker，**后**把它放到 externalBin 要求的位置 |

于是「编译 worker」这一步被它自己要产出的文件挡死。

**修法**：让 staging 这次编译**不校验** externalBin —— 用 tauri 官方的 config
覆盖入口 `TAURI_CONFIG={"bundle":{"externalBin":[]}}` 只作用于这一次 `cargo build`；
之后的 `tauri build` 不带覆盖，正常校验并把它收进安装包。

**这是先做实验再改的**：单独跑一次带覆盖的 `cargo build --bin extract_worker`
拿到 `exit=0`（1m59s），才去改脚本。

> **可复用的判断**：报错说「资源不存在」时，先问「**它该在什么时候存在**」。
> 配置本身可能是对的，错的是**两个步骤互相要求对方先完成**。
> 这类死锁的报错永远指向配置文件，而配置文件是无辜的。

### CI：一个会让 CI 假红/假绿的版本冲突

`pnpm/action-setup` 原写死 `version: 9`，而 `package.json` 的
`packageManager` 是 `pnpm@10.34.5`、lockfile 也是 10 生成的。
CI 用 9 去 `--frozen-lockfile` 装 10 的 lockfile，属于
「本地明明过了」的经典成因。改成不写 version（action 自己读 `packageManager`），
`node-version-file: package.json` 同理。

同时给 `bundle` job 加了**必须断言的两项**：

- **worker 真的 staging 了**（漏掉它时编译与打包都会成功，只有用户第一次用 AI 模式才会发现解析不了）；
- **安装包 SHA-256**（未签名包唯一的来源验证手段）。

### 截图暴露的第二个缺陷：全新计划说「计划已被修改」

采集预览页截图时发现，一个**刚生成、用户什么都没改**的计划，执行按钮旁边写着：

```
• 计划已被修改，请重新预览后再确认。
• 存在阻断项，无法执行。请先解决上面的问题。
```

两句都不成立：可执行项数那时是**未知**（界面自己都显示「—」），阻断项还没校验过。

根因在两处：

1. `disabledReasons` 用「`planRevision !== reportRevision`」当「被改过」的判据，
   而 `planLoaded` 只把 `planRevision` 设成计划版本、`reportRevision` 留在 0
   → **全新计划天然「不一致」**，于是永远走「被改过」那一支；
2. `invalidate()`（编辑时）把整个 confirmation 重置成 `EMPTY_CONFIRMATION`，
   **连 `reportRevision` 一起清零** → 「从没校验过」与「校验后又被改」
   变成完全相同的状态，再也分不开。

**修法**：

- `invalidate()` **保留** `reportRevision`（`state.report` 本来就跨编辑保留，
  抹掉版本反而与它不一致），只清令牌；
- `disabledReasons` 以 `reportRevision === 0` 判定「从未校验过」，
  分成「去点校验」与「计划已失效」两条不同的话；
- 「一项都不可执行」这条理由只在**校验结果确实对应当前计划**时才给，
  否则那个 0 的含义是「还不知道」。

**测试**：先写探针（两条变红，DOM 快照里就是上面那两句），修完 28/28 通过；
另加一条 reducer 级用例钉住「编辑只清令牌、不清版本」这个机制本身。

> **可复用的判断**：`EMPTY_*` 常量被当作「重置」到处用时，
> 很容易把**判断依据**也一起重置掉。重置状态前先问一句
> 「这里面有没有哪个字段是**事实记录**，而不是状态？」
> 事实（校验过、版本是多少）不该被 UI 状态的重置带走。

### 发布物内容扫描：两个 exe 里带着编译机的用户名

规格 T16 有一条：「发布内容不包含真实路径样本、API Key、模型返回原文或用户资料」。
把这条做成了一条命令（`scripts/scan-release-content.py`）后，第一次跑就命中：

| 命中 | 性质 |
|---|---|
| `scripts/cleanup-temp.py` 写死本机开发目录 | 会进公开仓库的真实路径样本 → 改成从 `__file__` 推导，且**默认只预演** |
| `docs/PROGRESS.md` 一条环境备注写了绝对路径 | 同上 → 改成占位形态 |
| **`filepilot.exe` / `extract_worker.exe` 内嵌编译机用户路径** | 见下 |

二进制里的路径来自**依赖 crate 的 panic 位置**（`file!()` 是编译期字面量）：

```
C:\Users\<用户>\.cargo\registry\src\...\anyhow-1.0.104\src\error.rs
```

`strip = true` 去不掉它——它不是调试信息，是字符串字面量；
泄漏的是 `.cargo\registry` 而不是项目目录，因为依赖比我们的代码 panic 得更多。

**修法**：`scripts/build-desktop.py` 统一给 release 构建加 `--remap-path-prefix`
（项目 → `.`、registry → `/cargo`、toolchain → `/rust`），用
`CARGO_ENCODED_RUSTFLAGS` 传（`RUSTFLAGS` 会被 cargo 按空白切分，路径带空格就坏）。
代价是一次全量重编译，这在注释里写明了。

**验证**（重建后重跑同一个脚本）：**0 类命中**（原 2 类）；逐字节复核
`cj169` / `Desktop` 都已消失、`/cargo` 出现。安装包随之重建，
旧哈希作废（详见 `docs/TEST_MATRIX.md` 8.5）。

> **可复用的判断**：「发布物里有没有不该有的东西」这类要求，
> 只要**能被脚本判定**就不该留在人眼清单上——清单上写「逐项检查」，
> 实际结果是没人逐项检查，而泄漏一直躺在安装包里。
> 同时要划清它**证明不了**的边界（NSIS 固实压缩扫不了），那一格继续留给人工。

### 设置页：密钥的生命周期短到「提交那一刻」

`ProviderSection` 里没有、也不该有「显示/隐藏密钥」的开关：
**能显示就意味着能读回**，而规格 3.3 明确排除了这个能力。

| 时刻 | 界面知道什么 |
|---|---|
| 用户输入 | `draft.secret` 这一个字符串（`type="password"`） |
| 提交 | 原样发给后端，**前端不做任何改写**（不做 trim——如果后端认为它有问题，应当由后端说了算） |
| 保存成功 | 立刻清空输入框。此后界面只知道「有一条密钥」 |
| 再次打开 | 输入框是**空**的，`placeholder` 说明「留空表示不改动已保存的密钥」 |

「留空 = 不改动」这个语义有一条测试把请求参数钉住（断言传的是 `null`
而不是空串），因为它是用户「只想改端点」时唯一的正确行为。

### 四项硬限制各由一个显式设置保证

规格 6.4 对「往外发请求」有四个要求。**每一个都对应 WinHTTP 的一个 API 设置**，
而不是「指望某个库的默认值恰好是对的」：

| 规格要求 | 落点 | 性质 |
|---|---|---|
| 代理环境变量不得把请求转发到外网 | `WINHTTP_ACCESS_TYPE_NO_PROXY` | **构造性**：不读系统代理，也不读环境变量 |
| 禁止跟随跨域重定向携带密钥 | `WINHTTP_OPTION_REDIRECT_POLICY_NEVER` | **构造性**：压根没有第二次请求 |
| 响应体上限 1 MiB | 自己数读到的字节，**先判上限再追加** | 代码执行 |
| 60 秒超时 | `WinHttpSetTimeouts` 四项 | 代码执行 |

### 端点校验：只认识少数几种形状

`Endpoint::parse` **不追求成为一个通用 URL 解析器**，它只认识被支持的形状，
其余一律拒绝。理由是一个具体的攻击输入：

```
http://127.0.0.1@evil.com/     ← 真正的主机是 evil.com
```

通用解析器会（正确地）解析成 `evil.com`，而人眼很容易读反。所以：
含 `@` 直接拒绝、含 `?`/`#` 直接拒绝、本地端点的 host 必须是 IP 字面量。

**`localhost` 在解析时就被换成 `127.0.0.1`**：名字要靠系统解析，
而解析结果可以被 hosts 文件改到任意地址。本地请求不该有这种可能性。

### 密钥不落盘的验证方式

T12 验收原文：「检索测试日志及 DB 导出不得出现测试密钥」。做法是三层：

| 层 | 断言 |
|---|---|
| 类型 | `ProviderSummary` 里**没有**能装密钥的字段；`ProviderConfig` 只有 `credentialRef` |
| 表结构 | `PRAGMA table_info(providers)` 恰好是 `id/kind/endpoint/model/credentialRef`，并逐一检查列名不含 secret/password/apikey/token |
| **字节** | 把 `.db` + `-wal` + `-shm` **整个读成字节**，搜不到测试密钥 |

第三层是关键：只读主文件是不够的——刚写进去的数据很可能还在 WAL 里。
而且这条测试**先断言密钥确实存进了凭据存储**，否则「数据库里没有」可能
只是因为压根没存，而不是因为存对了地方。

### 两个适配器共用同一套语义

规格要求「兼容适配器和 Ollama 适配器分别实现同一个
`suggest(batch, cancellation) -> Result<Vec<Proposal>>` 语义」，
所以**只有请求与响应的形状**是不同的：

| 共用 | 各自 |
|---|---|
| 系统提示（逐字来自规格 6.4） | 路径（`/api/chat` vs `chat/completions`） |
| 载荷构造（文件名 + 摘要，**无路径字段**） | 结构化输出字段（`format` vs `response_format`） |
| 输出校验（结构 + 数值范围 + 未知字段） | 响应提取（`message.content` vs `choices[0].message.content`） |
| 状态码分类（401/403 与 429/5xx 分开） | |

### 载荷里没有路径字段

`SuggestionItem` 里**没有**路径字段，与 T10 的工作进程协议是同一个思路：
让「把用户目录结构发出去」在实现上无从表达，而不是「需要被检查的约定」。
文件名的分隔符校验是第二道，有单测覆盖 `C:\Users\...\x.txt` 与 `../..` 这类输入。

### 已知限制

- **兼容云适配器的端到端无法用本地假服务覆盖**：规格要求兼容云端点必须是
  HTTPS，而假服务是明文 HTTP（给它配证书就变成在测 TLS 栈）。
  所以本地能验证的是**校验本身生效**；真正的 HTTPS 路径留给设置页的
  「测试连通性」在真机上验。适配器的解析逻辑由单测覆盖。
- **两处测试串行闸门**（`ai_contract.rs` 的 `NETWORK_GATE` 与
  `platform/child_process.rs` 的 `PROCESS_GATE`）。理由见 ADR-023 决策 6：
  一处是「产品本身就要求并发 1」，一处是「跑真实子进程的用例共用进程级资源」。
  两处都是**为了让门禁可信**——一条会因为环境而随机变红的测试，
  会把真正的回归淹没在噪声里。
- **`test_provider` 会真的发一次请求**（到用户配置的端点），这是规格 5.2
  要求的；它不发送任何用户文件（载荷由 `probe_batch()` 在编译期写死）。

### 2026-09-21 缺陷审查（T12 完成后）

用「可验证的手段」扫了一遍，不是通读。四类手段与结果：

| 手段 | 结果 |
|---|---|
| 前后端错误码集合对比 | **一致**（39 : 39）——但靠手工维持，见下 |
| Rust 命令 ↔ 前端 `CommandName` 对比 | **一致**（24 : 24，无缺漏） |
| 生产代码可疑模式扫描（`unwrap`/`panic`/`unreachable`） | 发现 1 处真问题 |
| **14 种敌意端点形状实测** | **全部被拒**（转成永久回归测试） |

#### 1. `extract_batch` 里的 `unreachable!` —— panic 会带走整批结果

那个函数的整个设计前提是「任何失败都变成一份 `Extraction`，不向外抛」
（它自己的文档就这么写的），而末尾却有一个 `unreachable!("上面已补齐")`。

补齐循环确实保证了它不可达，但**这与该函数的设计前提相矛盾**：
一旦将来有人动了那段循环，一个 panic 会让**整批**已经提取好的结果一起消失，
而用户要的恰恰是「能提多少提多少」。已改成生成一份带 `INTERNAL` 的结果。

#### 2. `note_discarded` 的注释与实现不符，且会泄露内容

它的文档写着「**只记原因，不记条目内容**」，但传进去的 `reason` 恰恰来自
`validate_proposal`——而那些消息里带着模型返回的 `category` 与 `stem` 原文，
模型又往往保留用户文件名的一部分。

debug 构建下 `eprintln!` 会把它打进 **stderr**，也就是测试与 CI 的日志，
而规格 3.3 明确禁止日志包含文件正文。已改成只记**类别**。

#### 3. 前端错误码集合靠手工同步（加测试根治）

`KNOWN_ERROR_CODES` 是手写的，与 Rust 的 `codes` 之间原先没有任何自动比对。
这个缺口**真实发生过两次**（T11 的 `OCR_UNAVAILABLE`、T12 的两个新码），
后果是界面把「去凭据管理器看看」这类有下一步动作的提示降级成「未知错误」。

新增 `tests/ui/error-codes.test.ts` 直接读 Rust 源码比对。
跨语言读取不算优雅，但它守的是一个已经发生两次的缺陷，代价只有一次文件读取。

#### 4. 一条测试的断言强度：黑名单 → 白名单

`the_item_type_has_no_path_field_at_all` 原先断言「序列化结果里不出现
path / dir / C:」。黑名单只能挡住想得到的那几种名字，而「悄悄加一个
`targetPath` 字段」恰恰是想不到的那种。已改成**枚举允许出现的字段**，
新增字段必须先改测试——而改的人会看到旁边那句规格原文。

#### 5. 端点校验的强度有了实测证据

新增 `hostile_endpoint_shapes_are_all_refused`：14 种「看起来像回环、
实际不是」的写法（`2130706433`、`0x7f.0.0.1`、`0177.0.0.1`、`127.1`、
`127.0.0.1.evil.com`、`evil.com#@127.0.0.1`、IPv4 映射地址……）**全部被拒**。

能全拒的原因是一条构造性性质：本地端点的 host 必须能被
`IpAddr::from_str` 接受，而那个解析**只认标准写法**——别的语言与别的库
是认识 `2130706433` 的。另有一条测试单独钉住这个前提，
免得哪天换了解析方式之后上面那些拒绝悄悄失效。

#### 6. 死代码扫描：找出「定义了但没有调用方」的公开函数

367 个 `pub fn` 里有 32 个没有任何调用方。逐条看下来分三类，
**第二类是真正值得查的**：

| 类别 | 例子 | 处理 |
|---|---|---|
| Tauri 命令 | `get_settings`、`start_scan`… | 误报——它们由 `generate_handler!` 宏注册，脚本看不到 |
| **漏接线的能力** | `platform::ocr::max_image_dimension`、`platform::windows::is_hidden_or_system` | **见下两节，都是真问题** |
| 纯死代码 | `repositories::delete_provider` | 删掉（见下） |

#### 7. `walk.rs` 绕过了 platform 层，重复定义 Win32 常量（架构违规）

对照规格 3.2：「platform/windows：…**这一层之外不允许直接调用 Win32**。」

`scanner/walk.rs` 自己定义了 `FILE_ATTRIBUTE_OFFLINE` / `HIDDEN` / `SYSTEM`
三个常量并做位运算，而 `platform/windows.rs` 里**已经有一个
`is_hidden_or_system`**，它却无人调用。结果同一套规则被抄成两份——
而「跳过隐藏文件」这种规则出错时不会报错，只会安静地少跳过或多跳过一些文件。

已把属性位与判断收敛进 `platform::windows::attributes`（常量 + 三个纯函数），
`walk.rs` 与 platform 自己的按路径版本都调它们。**规则只写一次。**

> 同时提供「按位」与「按路径」两个入口是有意的：扫描器**已经拿到了
> metadata**，让它为了一个位判断再按路径取一次属性，是按文件数的额外系统调用。

#### 8. `max_image_dimension` 没接线：超长边被误报成「文件损坏」（真缺陷）

`platform::ocr::max_image_dimension` 的文档写着「系统有硬上限，超过会直接报错」，
但它**没有调用方**——`extractors::image` 只检查「≤2000 万像素」。

这是两条**不同**的限制。**实测本机 `MaxImageDimension = 10000`**，
于是一张 `10001 × 1900` 的图：1900 万像素，过得了我们那关，
却会被引擎拒绝——而拒绝的表现是「识别失败」，一路映射下来变成
`EXTRACTION_CORRUPT`。

**那等于告诉用户「文件损坏」。** 文件没坏，只是太宽，而「缩小图片」与
「换个文件」是完全不同的动作。已加第二条检查（边长），报 `EXTRACTION_TOO_LARGE`，
并补了两条边界测试（超限被拒、正好等于上限**不**被当成超限）。

#### 9. `tests/scan.rs` 的静默 `return` 改成了硬断言

S02（重解析点不被跟随）有两处 `eprintln! + return`。它写着「这不算通过」，
但 **cargo 只在测试失败时才显示 stderr**——所以静默跳过时用户看不到那句话，
测试**仍然是绿的**。

而它守的是「不跟随重解析点走出批准范围」这条安全边界。
已改成硬断言（本机实测 `mklink /J` 可用且不需要特权，T11 也验证过）。
顺带把它的 `FILE_ATTRIBUTE_REPARSE_POINT` 换成 platform 层的判断。

#### 10. `repositories::delete_provider` 是纯死代码

没有命令调用它（规格 5.2 的命令表里**没有** `delete_provider`），
也没有测试。而它的注释里提到了一个不存在的 `commands::delete_provider`
——那是当时写作时的假设，不是事实。已删掉。

> **这一条与「漏接线」的区别值得记住**：`max_image_dimension` 与
> `is_hidden_or_system` 是**规格要求的能力**没被用上（真缺陷）；
> 而 `delete_provider` 是**规格没有要求**的东西多写了（纯冗余）。
> 两者都表现为「没有调用方」，但处理方式相反：前者要接线，后者要删。

### T13 起步（二）：`ai/disclosure.rs` —— 载荷冻结与授权

`ai/disclosure.rs`（此前已写好但**未注册进 `ai/mod.rs`**，所以从未参与编译）
现在接上了。它是规格 6.4 那句「**不重新拼接未展示内容**」的落点。

| 项 | 落点 |
|---|---|
| 冻结载荷 | `FrozenPayload::seal(...)`：instruction / mode / providerId / model / 逐个文件（名字 / 扩展名 / 源指纹 / 实际文本） |
| 摘要 | `canonical_form` + SHA-256，字段用 **`\x1f` 分隔**（见下） |

| 授权 | `ConsentStore::grant(payloadDigest, providerId)` —— 只认摘要 + 提供商 |
| 取回 | `ConsentStore::resolve(consentId)` —— **取**，不是**算** |
| 开始前比对 | `verify_start(payload, StartRequestFacts)` —— 逐字段比，**并指出是哪一项** |
| 载荷构建 | `build_payload(...)`（本轮新增）：从本地已拿到的文件与正文产出冻结载荷 |

#### 摘要为什么不用逗号拼

`报告.tar.gz` 与 `["a,b", "c"]` 这类输入说明了一件事：字段用可打印分隔符拼接时，
`["a,b", "c"]` 与 `["a", "b,c"]` 会拼出**同一个串**，于是两份**不同的**载荷
共用一个摘要 —— 而摘要正是授权的依据。所以用不可打印的 `\x1f` / `\x1d`，
并且有一条测试专门钉住「字段边界不能被内容伪造」。

#### 本轮修掉的两处

1. **`file_name` 的文档与实现不符**。注释写的是「展示名（文件名 + 扩展名）」，
   而实现与测试都是「**不含**扩展名」。这是文档在骗人 —— 而载荷的字段含义
   正是最不该说错的东西。已改正，并让 `build_payload` 明确剥扩展名。
2. **`truncated` 用「字符数 >= 上限」推断，会产生假阳性**。原文**正好**
   2,000 字符时并没有被裁，界面却会说「这段被截断了」—— 一句不真的话。
   已改成由构建时记录这个事实，并补了两条边界测试（超限标记、正好等于上限**不**标记）。

#### `build_payload` 里两处容易错的地方

- **文件名按已知扩展名剥，不按「最后一个点」切**。`报告.tar.gz` 的扩展名是
  `gz`，剥掉之后是 `报告.tar`；按第一个点切会得到 `报告`，丢掉对「按类型分类」
  有用的信息。有测试钉住。
- **扩展名与文件名对不上时不拼接**。那种数据不一致下保留完整文件名、扩展名置空，
  否则展示名会变成 `报告.PDF.txt` —— 一个从来没存在过的文件名。

#### 已知缺口（T13 未完成的部分）

- 三条命令 `preview_disclosure` / `grant_disclosure` / `start_analysis` **尚未接线**。
  规格 5.2 的签名与 `StartRequestFacts` 的字段是逐项对应的，接线时照抄即可。
- `start_analysis` 需要的「从 scanId + selectedFileIds 取文件记录与正文」
  还没写：正文要经 `platform::cache::SessionCache`（T11）取，
  缓存未命中时现场提取。
- `evidenceLocator` 的匹配校验（规格 6.4 末段）仍未做 —— 见上文 T13 清单。
- `ai::budget` 的重试循环与格式修复仍未接线。

### T13 起步（三）：三条命令接线

`src/commands_analysis.rs`：`preview_disclosure` / `grant_disclosure`
（`start_analysis` 见「已知缺口」）。命令体很薄，主体在 `build_preview` / `grant`
里 —— **`State` 在集成测试里构造不出来**，而「授权绑定的是用户看到的那一份」
必须在真实存取路径上验证。

`AppState` 补上它一直缺的两样：

| 字段 | 为什么要加 |
|---|---|
| `disclosures: ConsentStore` | 规格「程序重启后重新预览授权」→ 运行期状态，不落库 |
| `extraction_cache: Mutex<SessionCache>` | 规格 8.1：正文「仅内存或会话临时缓存」；它同时让「改一次 instruction」不必把整批文件重新提取 |

#### 本轮被测试抓住的一个真实 bug

`tests/analysis.rs` 里那条「预览里要能看到真实正文」红了，输出是
`character_count: 0` —— **正文全空**。根因是缓存键用错了：

- **写**用 `Extraction.source_fingerprint`（提取时算的快照，带 `sha256`）
- **读**用 `FileRecord.fingerprint`（扫描时的，可能还是 `None`）

两者**不是同一个东西**，而 `SessionCache::get` 靠指纹相等判断，于是
**永远不命中**：每一次预览都重新提取一遍，而正文始终是空的。
已改成读写都用记录里的指纹。

> 这条值得记：缓存键取错时**不会报错**，只会安静地每次都 miss。
> 而它的症状（空正文）看起来像是「提取坏了」——真正的原因在两层之外。

#### 顺带补上的一个规格缺口

规格说「本地模式 `consentId=null`」，而 `ConsentStore` 原先只有
`resolve(consent_id)` —— **本地模式根本取不回载荷**。补了 `resolve_latest()`：
取最近一次预览，不要求授权（本地数据不出本机）。它**不检查模式**，
那条规则由 `start_analysis` 执行 —— 否则「传 null 就能跳过授权」会成为
绕过云端授权的一条路。

#### 一个被顺手修掉的并发源头

`extractors::image` 有一条用例在全量跑时偶发失败（单跑必过）。原因是我在
`extract()` 里加的边长检查引入了 **WinRT 调用**，而 `image` 的每条用例都会
经过它——并行跑测试时，那是一片同时压向 WinRT 的调用。

修法不是加锁，而是**缓存**：`max_image_dimension()` 的结果是**引擎的属性，
不随线程变化**，问一次就够（这一点与 `ensure_initialized` 正相反——公寓是
线程级的，必须每次初始化）。缓存之后，并行时只有第一个线程会真调 WinRT。

连跑三次 lib 全量（395 条）**均通过**，不再偶发。

### T13 起步（五）：重试与格式修复接线

规格 6.4 那两句话里的判定函数（`Retry::of_status` / `backoff_delay` /
`allow_retry` / `allow_repair`）从 T12 起就写好了，但**没有任何代码调用它们**
——属于「规格要求没接线」。现在接上了（`commands_analysis::suggest_with_retries`）。

| 情况 | 动作 |
|---|---|
| 可重试（429 / **可恢复** 5xx） | 退避后再问一次，最多 2 次 |
| 输出不是合法 JSON | **修复**：再问一次并明确要求 JSON，最多 1 次 |
| 其他（401/403 等） | 直接返回——重试多少次都是一样的结果 |

#### 两张表共用一条规则

「哪些状态码可重试」原先在两处会各写一遍：重试循环按它决定要不要再试，
而 `ensure_success` 按它决定要不要把 `retryable` 置位给界面看。
两条规则漂移的结果是「界面显示可以重试、而实际不会重试」（或反过来）。

所以 `ensure_success` 现在**调用** `ai::budget::Retry::of_status` ——
顺带也修正了一处不精确：原先 `500..=599` 全都算可重试，而
**`501 Not Implemented` 不是**（它说的是「这个端点不支持这个功能」）。

#### 修复**不得**改变要发送的内容

修复时在用户要求后面追加 [`REPAIR_SUFFIX`]：一段**固定文本**，只谈格式，
不含任何来自本次请求的内容。

这不是细枝末节：如果修复顺手「调整」了正文或文件集合，那么用户看到并授权的
那一份就不再是实际发出去的那份。所以有一条测试专门比对**两次请求里逐一相同
的文件列表**，而不只是比对「修复之后能成功」。

#### 一条被 `let _ =` 掩盖过的问题

一条测试原先写成 `let _ = run_analysis(...)`，于是「分析其实失败了」表现成
「服务端没收到请求」——而那个症状会把排查方向引向网络与服务端。
改成 `.expect(...)` 之后问题自己浮出来了。

> **测试里不要吞错误**，尤其是「发请求」这类动作的返回。吞掉之后，
> 失败的样子与真正的原因之间往往隔着好几层。

### T13 起步（六）：`evidenceLocator` 核对

规格 6.4 末段：

> `evidenceLocator` 必须匹配本次提取的真实定位信息，前端证据片段从本地
> 提取结果读取，**不接受模型自造引用**。

#### 为什么校验放在分析服务，而不是 `parse_proposals`

规格规定了 `suggest(batch, cancellation)` 的签名，而 `batch` 里**没有**
证据定位——那种「本地有、但不发给模型」的东西不该混进发给模型的形状里。
所以核对放在分析服务里（`drop_fabricated_evidence`），紧跟在 `suggest` 之后。

#### 编造的引用被**清掉**，而不是丢掉整条建议

分类与命名才是模型的主要产出，引用只是它的**出处**。一个编造的出处说明
模型在这一点上不可信，但不该让它给出的分类一起作废——那对用户是净损失，
而他看到的会是「模型没有给出建议」：真实原因（模型引用了不存在的位置）
永远不会浮出来。

前端按 locator 去**本地**提取结果里取片段，取不到就不显示，所以被清掉的
引用不会在界面上留下任何假证据。有两条测试分别钉住「编造的清掉」与
「真实的保留」——只有前一条的话，**「把所有引用都清掉」也能通过**。

#### `SessionCache` 改成存整份提取结果

原先它只存正文（`(Fingerprint, String)`），而证据定位是同样有价值的提取
产物。只存正文的话，那条核对就得在每次预览时**重新提取一遍**才能拿到定位
——而重新提取的结果未必与当初发送的那一份一致（文件可能被改过、OCR 可能
给出不同的分页），核对也就变成了一件说不清的事。

现在存 `(Fingerprint, Extraction)`，正文与证据一起命中。顺带补了一条
「缓存也应当留住证据定位」的测试。

### T13 起步（四）：`start_analysis` —— 规格验收达成

规格 T13 的验收原文是：

> **假服务观察到的请求内容与授权预览完全一致。**

这一条**已经做到**（`tests/analysis.rs`）。它能做成本地端到端，靠的是一个
此前的限制反过来变成了条件：**本地模式要求 loopback，而假服务正好在
`127.0.0.1` 上**。（兼容云端点被要求是 HTTPS，所以那条路仍然只能用真机验。）

#### 端到端验的是哪几件事

| 断言 | 它挡的是什么 |
|---|---|
| 请求里的 `instruction` == 预览里的 | 发送路径自己拼一份要求 |
| 请求里的文件数 == 预览的 `fileCount` | 悄悄多发或少发文件 |
| 每个 `fileId` / `fileName` 与预览逐项相同 | 发的是另一批文件 |
| 摘要是预览里那段正文的**开头** | 预览与实际内容不一致 |
| 请求**载荷**里没有目录名、没有路径分隔符 | 「不发送绝对路径」（夹具把文件放进 `工作/` 子目录，否则这条断言无论对错都会通过） |

#### 「传 null 不等于跳过授权」

规格说「本地模式 `consentId=null`」，于是 `None` 这条路上**必须**确认拿到的是
本地模式的载荷。`resolve_payload` 就是这条规则唯一被执行的地方——否则
「传 null 就能免授权」会成为绕过云端授权的一条路。有两条测试分别钉住
「云端没有授权 id 会被拒」与「授权之后能拿到**冻结的那一份**」。

#### 分析记录

`analyses` 表（T01 就建好了，字段与规格 5.1 逐项对应）现在真的被写入：
`status`、`proposalJson`、**`inputFingerprintsJson`**、**`promptVersion`**。

后两个是事后追责的抓手：没有它们，「这次分析基于哪一版文件」与
「这条建议是哪一版提示词产生的」都没有答案。

夹具里有一段**必须照做的落库**：`store_scan` 只写内存，而
`analyses.scanId` 有一条外键链指向 `scans` → `roots`。真实的 `start_scan`
命令也是先落库再改内存的（它的注释写着「create_plan 才不会撞 scans 的外键」）
——夹具不照做，测的就是一个界面走不到的状态。

#### 本轮我写错的四处（都是测试代码或断言，不是实现）

1. 一条测试**没有先预览**就断言「云端拒绝」——于是先撞上「还没有预览过」，
   断言里的错误码对不上。修法是补上预览，让被测的那条规则真的被执行。
2. `Vec<Value>` 没有 `Display`，不能直接 `to_string()`。
3. 夹具少了落库，撞外键。
4. 「请求体不含反斜杠」这条断言**太宽**：系统提示里嵌着 JSON Schema，而
   Schema 里的转义换行（`\\n`）被误判成路径分隔符。改成只检查**载荷那一段**
   ——那才是这条断言真正要说的事。

### T13 起步（七）：`create_plan(analysisId)`

规格 5.2 的 `create_plan` 有两条路：`ruleKind`（规则）与 `analysisId`（AI）。
原先只有前者。现在把两者收进同一个命令，并**显式拒绝「都给」或「都不给」**

新增 `plan_from_analysis`（`commands_plan`），三道核对各自挡住一种「看起来正常
但实际错位」的计划：

| 核对 | 挡的是 |
|---|---|
| 存在 | 分析 id 过期或来自别处 |
| **属于同一次扫描** | 「建议来自 A、文件来自 B」的计划 |
| 已完成且能解析 | 把「还在跑」或「读不出来」当成空建议 |

第二条最要紧：错位的计划**看起来完全正常**——有文件名、有目标路径、有理由

它接受 `&Database` 而不是 `&AppState`：`AppState` 在集成测试里构造出来的那份，
与命令拿到的那份不是同一个东西的话，测的就**不是同一条路**。

#### 一处被测试纠正的理解

我原本断言「两个文件都要进计划」，实际是 **1 个** —— `build_plan` 只为

### T13 补齐：低把握与无依据的项默认不选中

规格 4.2 原文：

> 模型自报 confidence 只是排序信号，**不显示为「准确率」**。低于 0.80、
> 依据不足、解析失败或存在冲突的行**默认不选中**；较高分也必须由用户最终确认。

四条件里，`build_plan` 管前两条（解析失败在构建时就走不到 `Planned::Move`，
冲突要等 `validate_plan`——那一层才知道目标位置上有没有东西）。

「默认不选中」是**默认**，不是「不能做」：这些项仍然出现在预览里，理由也
写清楚（`LOW_CONFIDENCE`），用户想勾就能勾。

#### 一个差点造成灾难的照搬

「依据不足」这四个字**只对 AI 模式成立**。规则模式按扩展名分类，它本来
就没有、也不需要正文引用——把同一条规则照搬过去，结果是**规则模式的每一项
都不被选中**：界面看起来完全正常，只是没有任何东西会被整理。

这个 bug 不报错、不抛异常，只是什么都不发生。有一条测试专门守着它
（`a_rules_suggestion_needs_no_evidence`）。

## 已知问题：句柄/作业类测试偶发失败（T11 遗留）

`platform::child_process::tests::a_handle_that_was_not_listed_is_not_inherited`
在 `cargo test --lib` 全量跑时**偶发**失败：

- **`std::env::set_var` 污染进程环境** —— 全仓库只有 `bin/recovery_crash_child.rs`

- **并发度相关** —— `--test-threads=1` 也失败。

**当前判断**：这些用例跑**真实子进程**并检查**父进程内的句柄值**，而句柄值

**下一步应该做的**（还没做）：按「跑真实子进程的用例要串行且与其它模块隔离」

### T13 补齐（二）：非法输出夹具抓出一个真实缺陷

规格 6.4 的 checklist 要求「提供模型输出夹具覆盖所有第 6.4 节非法情况」。
`tests/ai_contract.rs` 里新增了一组夹具，逐条对着那句话列：

> 拒绝未知/重复 fileId、重复条目、越界 confidence、**非法路径**、过长字段。

每种情况**单独成批**（而不是合并成一条大 JSON）：一条不合法就整批失败的话，
你无法知道模型到底犯了哪一种错。另有一条反面对照（合法输出要能通过），
否则「全部拒绝」也能让每一条通过。

#### 被夹具抓到的缺陷：`..` 能穿过第一道校验

`["..", "Windows"]` **通过了** `parse_proposals` 的校验。

`planner::build::validate_category` 早就拦了它，但那是**第二道**——
而模型输出的第一道（`ai::provider::validate_proposal`）没拦：

- 第二道是给「用户手改的计划」用的，它的输入被假定已经过第一道；
- 一条穿过第一道的不合法建议，在下游任何一处「忘记再查」的地方
  都会成为真实路径。

修法是把名字组件的校验抽成 `validate_name_component`（目录跳转、分隔符、
Windows 保留字符、**组件长度**），category 与 stem 共用。顺带补上了
「分类目录名也受 80 单位限制」——规格 7.1 说的是「单个**名称组件**」，
不只是 stem。

#### 提示注入

两条测试，问的是**结果**而不是「我们有没有过滤掉那句话」：

1. **模型夹带未知字段**（`"command": "delete"`）→ `Proposal` 带
   `deny_unknown_fields`，整批被拒。这个取舍是对的：宁可整批拒绝，
   也不要「跳过不认识的字段继续用」——后者意味着模型的输出形状可以
   悄悄偏离约定而我们不知道。
2. **所有字段都合法、只是 reason 里写着「删除所有文件」** → 必须能通过
   解析（那只是一句说明文字），而**不能**变成任何动作。断言方式是列出
   `Proposal` 的全部字段名，确认里面**没有**表达动作的字段：
   模型能影响的是「分类、名字、理由、把握」，不是「做什么」。

#### 一处被牵连的旧测试

`the_total_path_limit_is_enforced_at_exactly_240_units` 挂了，因为它构造的
建议是 `confidence: 1.0` + **无依据** + AI 模式——正好撞上刚加的「无依据
默认不选中」。它验的是**路径长度**，与依据无关，所以给夹具补上依据。

> 两个维度都不满足时，失败信息会抱怨一件与测试想问的问题无关的事。

> 状态以 taskId/planId/revision 为依据，**忽略旧请求返回**，不让前一个分析
> 覆盖新计划。

各页面原先有 `let cancelled = false` 的清理函数，但那只防**组件卸载后
setState**，不防「组件还在、状态被旧数据盖了」。

#### 真实竞态：先发后回的旧预览

用户快改两下要求，于是有两个 `preview_disclosure` 同时在飞 —— 而**先发的
后回**。它带回来的是**旧要求**对应的预览，而用户正盯着屏幕以为自己看的
是新要求的内容。

这个错误最坏的地方是它**看起来完全正常**：有文件名、有字符数、有内容开头，
只是全部对应上一次的输入。用户据此点「确认并授权」，授权的就是一份他以为
已经改掉的载荷。

后端的摘要校验会挡住它（载荷确实变了），但那时用户看到的是一句「载荷已
变化」—— 一句与真实原因（「你的前一个请求回来晚了」）完全对不上的话。

修法是给 `useAiDisclosure` 加一个**单调递增的请求序号**：只接受最新那次
的结果，旧的回来时直接丢掉（成功和失败都丢）。`reset()` 也会作废在飞的
请求——用户已经重新开始了，它的结果不该再落到界面上。

三条测试用**可延后兑现的 promise**（而不是 `setTimeout` 猜顺序）精确控制
「谁先回来」：旧的成功回来不覆盖、旧的失败回来不打回起点、reset 之后
在飞的请求不落地。

#### 还差什么

`PreviewPage` / `HistoryPage` / `RecoveryPage` / `UndoPage` 的加载仍是
「卸载防护」而不是「旧响应防护」。它们的风险低一些（多是单向加载，
不像 AI 预览那样会被连续编辑触发两次），但 T14 那句话是对**所有**状态说的
——这几处还没改。

#### 虚拟列表：为什么不是分页

规格说的是「**虚拟列表**」——用户看到的仍然是一张连续的表，可以一路滚下去。
分页会把「这一页选中的项」变成一个新的状态要维护，而「**筛选和编辑不丢
选中状态**」正是同一句话的下半句：多一个状态就多一处会丢的地方。

所以选中状态仍按 `itemId` 存在 reducer 里，窗口化只影响**渲染哪几行**：
滚出去的行被卸载，但它的勾选与草稿留在状态里，滚回来时照旧。

**行高必须是常量**（`PLAN_ROW_HEIGHT = 40`，与 CSS 里同一个值）：占位高度 =
行数 × 行高，行高变成「渲染后才知道」的话，占位高度就只能靠猜——而猜错的
表现是**滚动条长度随滚动乱跳**。有一条测试专门验「上 + 渲染 + 下 = 总数 × 行高」。

#### 两条容易图省事的路都堵上了

1. **不用 `useRef` 存容器**。本项目启用了 React Compiler 的 `react-hooks/refs`
   规则，而它的判定**很保守**：只要调用一个内部用过 `useRef` 的 hook，
   **返回值的每一个属性**都会被当成「在渲染期访问 ref」——连 `paddingTop`
   这种纯数字也报。改成 state 之后语义反而更准：容器**确实**参与渲染
   （它的高度决定渲染哪几行）。
2. **`scrollToIndex` 删掉了**。它要写 `container.scrollTop`，而那被判定为
   「修改不可变值」。它当时也没有任何调用方——与其为它找一个绕过 lint 的
   写法，不如不留没人用的代码。

#### 一处 lint 误报与处置

`ref={windowed.attachContainer}` 仍被 `react-hooks/refs` 判为「渲染期访问
ref」。那**是误报**——回调 ref 这个模式的全部要点就是「不读 `ref.current`」。
就地 `eslint-disable` 并写明理由，而不是为了过 lint 把代码改成更难懂的样子。

#### 无网络启动

核查结果：启动路径只调 `get_settings` / `recovery_status` / `list_runs`，
全是本地读；`test_provider` 只在设置页由用户**手动点击**时触发。

**但这件事原本没有任何东西挡着它被破坏**：将来谁在 `App.tsx` 里加一个
`useEffect` 顺手探一下提供商，断网时就会卡住或报错——而**那种回归不会让
任何现有测试变红**，只会让「断网也能用规则整理」这个承诺悄悄失效。

所以加了 `tests/ui/startup-offline.test.tsx`，从**两个方向**钉住它：
「不许有会联网的命令」+「只允许那几个本地命令」。两个方向都要有——
否则「什么都不调」也能通过第一条。

### 性能结果

`--release`：10,000 文件扫描 **2.398 s**（目标 ≤15）、1,000 项计划 **0.255 s**
（目标 ≤2）、峰值工作集 **49.8 MB**。10 轮扫描 0.144 → 0.136 s，无累积。

**一条要一起说的**：造这 10,000 个样本本身花了 **401 秒**，而扫描它们只用
2.4 秒。差别来自杀软对**每一次 `fs::write`** 的实时检查。引用「10,000 个文件
要多久」时这个区别很重要——整理既有文件不会遇到那 401 秒。

### 哈希的进度与取消（新实现）

`sha256_of_handle` 原先**既没有进度也没有取消**：一个几 GB 的文件要跑几十秒，
而界面上只是一个卡住的窗口，用户会合理地以为程序死了。

加 `HashControl { on_progress, is_cancelled }` + `sha256_of_handle_controlled`
（返回 `Result<Option<String>>`），旧签名委托它。两个设计决定：

1. **取消返回 `Ok(None)`，不是 `Err`** —— 取消是用户的选择，不是失败。
2. **先查取消再读** —— 反过来的话，一次已开始的读无法打断。

### 一条写错的测试给出了有用的事实

`the_controlled_and_plain_paths_agree` 一开始红了：我在**同一个 `File` 上
连算两次**，而 `sha256_of_handle` **从当前位置读到末尾**。

这个语义**从没被写下来过**。修法不是改断言，而是把它写进函数文档——
**根因是文档缺了一句，不是测试写错了**。

| 可疑模式扫描 | **1 处真问题**（见下） |
| 承诺式注释抽查 | 「100 MiB 上限」与 `MAX_HASHABLE_BYTES` + `TOO_LARGE` **一致** |

### 扫出来的真问题：执行路径上的 `unreachable!`

`sha256_of_handle` 里原本写着：

```rust
unreachable!("不取消的控制不可能让哈希返回 None")
```

它**逻辑上**确实不可达（`HashControl::default()` 永不取消）。但这个函数在
**执行路径**上（`safety/fingerprint.rs` 调它），而一个 panic 会炸掉整批
已经完成的工作。**一个不可能发生的分支，不值得用那种代价表达。**

改成返回 `io::Error`。有一条断言守着「普通路径与受控路径给出同一个哈希」，
所以这个改动是安全的。

> 判断「`unreachable!` 该不该留」的标准不是「它是否真不可达」，而是
> **「万一它可达，代价是什么」**。

### 2026-09-21 修掉的真实缺陷

#### 1. 汉字之间的空格让 OCR 结果**搜不到**（功能缺陷）

这是本轮最有价值的一条，因为它是**先跑起来才看见的**，读代码看不出来。

实测一张写着「会议纪要」的图：

```
text = "会 议 纪 要 项 目 进 度 报 告 2026"
```

Windows OCR 按字符切分 CJK 词边界，每个汉字之间塞了一个空格。
这份正文是要拿去检索的——用户搜「会议」，在 `会 议 纪 要` 里**一个都搜不到**，
而 T11 验收原文写的正是「OCR 有文字时返回可搜索片段」。

修法见 ADR-022 决策 2：吞掉**两侧都是 CJK** 的空白，同时保留
`报告 2026` 这种真正起分隔作用的空格，且不碰用空格分词的韩文。

#### 2. 图片的错误码分流与文本 / PDF / DOCX **不一致**

第一版把图片的所有错误都映射成 `Unsupported`。于是同一个
`EXTRACTION_CORRUPT`：损坏的 DOCX 报 `Failed`，损坏的 PNG 报 `Unsupported`。

用户看到的会是「不支持此格式」，而那份文件本该能读、只是坏了。
第三行是 `unsupported()` 自己的文档——「把两者混为一谈，会让一个坏文件
看起来像一类正常文件」。

#### 3. junction 用 `remove_file` 删会**永远清不干净**

`purge` 原本对缓存目录里的重解析点调 `remove_file`，实测恒返回
`ACCESS_DENIED`，链接留在原地，每轮清理报一条 `skipped`。

用户看到的是「明明点了清理，缓存里还是有东西」，而且他没有任何办法自己修好。
正确删法是 `remove_dir`（只删链接本身）。三条实测事实见 ADR-022 决策 3。

> 顺带确认了一条**没有**发生的坏事：Rust 把 junction 判成链接而非目录，
> 所以不会递归进去删掉目标——**数据是安全的**。这个担心是我一开始的假设，
> 实测证明它不成立。

#### 4. `OnceLock` 缓存 `RoInitialize` 导致段错误

`RoInitialize` 是**每线程**的，WinRT 公寓绑定线程，而 libtest 每个用例一个线程。
把初始化结果缓进进程级 `OnceLock` 后，第二个线程调用时段错误
（`STATUS_ACCESS_VIOLATION`，退出码 139）。

修法两条：每次都调、不缓存；真实 OCR 调用整体移出进程内单测
（详见 ADR-022 决策 5）。

#### 5. 新增的错误码没同步到前端

T11 新增 `OCR_UNAVAILABLE`，但 `src/api/client.ts` 的 `KNOWN_ERROR_CODES`
是**手写**的，漏了它——前端会把这个码当成「未知错误」展示。

已补上，但**根因没有解决**：这个集合与 Rust 的 `codes` 模块之间没有自动比对，
也没有测试守着。要根治应当把它纳入契约生成物。已记在 ADR-006 的「已知缺口」。

#### 6. 一条 T10 测试因为「`--mode` 变成必填」而测不到它原本要测的东西

`the_worker_reports_a_usage_error_for_a_missing_handle` 原本传
`--version/--file-id/--format`（不带 `--mode`），靠 `validate()` 报出
「提取模式缺少 --handle」。T11 让 `--mode` 也成为必填后，`parse()` 先报
「缺少 --mode」，这条用例就测不到句柄那一支了。

修法不是放宽断言，而是**显式补上 `--mode extract`** 让它回到原意，
并另加一条 `..._for_a_missing_mode` 覆盖新模式。

> **「禁止联网」是构造性的，不是作业对象给的**：Windows 没有「这个进程不许联网」
> 的作业限制。它靠的是「工作进程不链接网络代码、输入里也没有 URL」。
> ADR-021 里如实写明了这一点，免得后来的人以为已经有机制在挡。

### 2026-09-20 修掉的真实缺陷（五处）

1. **句柄式目录删除恒失败**（T09 审查代码）：`open_directory_for_delete`
   的共享模式缺 `FILE_SHARE_DELETE`，`SetFileInformationByHandle(FileDispositionInfo)`
   一律 `ERROR_ACCESS_DENIED`。用四组「标志位 × 共享模式」对照实验定位——
   当时的直觉（怪 `FILE_FLAG_OPEN_REPARSE_POINT`）是**错的**。

2. **⚠️ 数据丢失：`FileDispositionInfo` 会删掉非空目录**
   修好上面那条之后，`a_directory_that_still_holds_user_files_is_left_alone`
   立刻失败，实测现场：**用户的文件随目录一起消失，且没有告警**。
   根因是本机 Windows 上该调用对**非空目录**也会成功并在句柄关闭时连内容一起删掉，
   直接违反规格 8.4 第 7 条的「非递归清理」。
   修法：删除前在**同一支句柄**上确认目录为空（`GetFileInformationByHandleEx`），
   并且共享模式**不带 `FILE_SHARE_WRITE`**——持有句柄期间别人放不进东西，
   于是「判空 → 删除」之间没有竞态窗口。
   新增永久回归测试 `created_directory_cleanup_never_removes_a_directory_that_still_has_files`。

   > **教训**：第 1 条让这个调用**恒失败**，而那层恒失败**掩盖**了第 2 条。
   > 修好一个「让功能恒失败」的缺陷之后，必须重新审视它掩盖了什么——
   > 恒失败的功能从来没有真正执行过，正确性一次都没被验证过。

3. **无项可撤销时整个撤销以 INTERNAL 失败**：`clean_created_dirs` 要把审计事件
   挂到真实操作上，而这时 undo run 里一条操作都没有。改为只在 `reverted > 0` 时清理。

4. **`text.rs` 的两处**：合法 UTF-8 快路径把 `suspicious` 硬编码成 0
   （同一份字节换个编码路径就得出不同结论）、比例判据对短样本过度惩罚
   （3 个字符里有 1 个可疑就判乱码）。

5. **句柄读取位置没有归零**（T10 自查发现，且被验收测试一次全红地抓出来）：
   * `sha256_of_handle` 从**当前位置**读到底。同一个句柄要取前、后两次指纹，
     第一次读完停在 EOF，第二次读到 0 字节 → 哈希不同 → **每个文件都被判成
     `SOURCE_CHANGED`**（25 条验收用例一次红掉 18 条）。
   * 更要紧的是：Windows 的文件位置属于 `FILE_OBJECT`，**被父子两支句柄共享**。
     父进程算完哈希后位置停在 EOF，工作进程继承到的就是「已经读完」的位置——
     不归零的话它读到空文件，而「提取到 0 个字符」会被下游当成「这文档没内容」。
   修法：父进程侧与工作进程侧**各自在读取前 `seek(0)`**。

详见 ADR-020 的两次更正与 ADR-021。

### 关键设计决定

**撤销沿用执行的那套安全原语，但换一对注入点。**
`MoveFailPoints::{Apply, Undo}` 让同一份 `move_no_replace_with` 在两条路径上
停在不同的点。不区分的话，「撤销在改名之后崩掉」这条路径根本无法单独验证——
而它恰恰是 §8.4 第 6 条唯一要防的场景。

**`undoStatus` 与 `status` 同样是两个维度。**
撤销成功**不改**原操作的 `status`（它当初确实 `applied` 了，那是事实），
只把 `undoStatus` 置为 `undone`。合并会丢掉「这一项曾经整理成功过」。

**「搬回」与「记 undone」必须在同一事务里落盘**（规格 5.1）。
分开写会留下「文件已经回去了、日志还说没撤」的窗口，那个窗口里的崩溃
会让用户再撤一次。`commit_revert` 把两条 UPDATE 和两条事件放进一个事务。

**摘要把操作 id / 撤销状态 / 当前判定算进去，但刻意不算「用户勾了哪几项」。**
勾选是用户看完清单之后才做的调整，磁盘事实一点没变；
把它算进摘要会让「取消勾选一项」变成「确认过期」，逼用户重新预览一遍。
勾选的合法性改由另一条规则保证：**只有当前判定为 `Ready` 的项才允许被选中**。

**requestId 由撤销计划 id 派生，不是每次点击新生成。**
每次点都换 id 的话，双击会被后端当成两个全新请求（INV-10）。

### 关键设计决定

**`OpStatus` 与 `OpResolution` 是两个正交维度，不合并。**
`status` 记「磁盘上现在是什么样」，`resolution` 记「用户对这件事做了什么决定」。
把「用户确认保留现状」写成 `status = skipped` 会抹掉「这一项其实没做成」这个事实——
审计记录必须能同时回答这两个问题。

**`resolution` 必须进 `state_digest`**（版本串从 `filepilot.run.state.v1` 升到 `v2`）。
否则「只确认了第一条」与「全部确认」摘要相同，用户能拿一份过期摘要提交整批确认。

**摘要校验必须整批、且在写之前。** 逐项校验会留下「前几条按旧事实确认、
后几条按新事实确认」的混合结果，比直接报错更糟。

**`items` 的语义是「本次调用真正看过的项」**，不是「库里所有未完成的项」。
它由调用方显式传入（`examined`），不由 `finish_from_operations` 从库重推——
否则重复核对时清单不会收敛，幂等断言会全部失效。

     用例名随之改为 `counts_give_ambiguous_its_own_bucket`——
     **名字说的是旧行为，就该一起改**，否则下一个人会照着一个骗人的名字写代码。

5. **`RecoveryPage` 在 effect 里同步 `setState`**（`react-hooks/set-state-in-effect`），
   后果是切换记录时会**先渲染上一份报告再清空**，用户看到别条记录的未决项闪一下。
   改为把「这份报告属于哪一次核对」一起存进 state，用渲染期判定代替 effect 清空：
   `loadedFor?.key !== \`${runId}#${reloadToken}\`` 就当作还没数据。

6. **`client.ts` 的命令白名单漏了 4 条恢复命令**（真实缺陷）
   `call<T>('get_recovery', …)` 会因为 `CommandName` 不含它而在
   `RESPONSE_CONTRACT` 查不到定义。补上命令名、响应契约与 `NULLABLE_RESPONSE`
   的说明（恢复命令一律返回真实报告，不允许为 `null`——
   「查不到」在这里是必须讲清楚的结论，不是「没有内容」）。

7. **全量测试偶发挂 1 条（非确定性，每次挂的用例还不一样）**

   症状：`cargo test --features failpoints` 全量跑时约每 2~3 次挂 1 条，
   单跑该用例、单跑该测试文件**必定通过**。挂过两处：
   `execute_windows.rs`（被选中的文件没被移动）与
   `validate_plan.rs`（自己刚写的文件 `write(true)` 打开被拒）。
   两次的退出都指向同一句话：`无法打开源文件: 拒绝访问。 (os error 5)`。

   排查过程（**关键在于取证而不是推理**）：我先猜了三个方向——
   取消回调的时序竞态、被杀子进程的残留句柄、扫描静默跳过——**全部被实验证伪**：

   | 实验 | 结果 | 排除的假设 |
   |---|---|---|
   | 单跑 `execute_windows` 并发 12 次 | 12/12 绿 | 二进制内竞态 |
   | `--test-threads=1` 串行 34 条 | 34/34 绿 | 进程内并发 |
   | 顺序跑 `recovery_windows` → `execute_windows` 8 次 | 8/8 绿 | 二进制间句柄残留 |

   最后给失败断言加上**一次性诊断输出**并连跑到复现，一次拿到真相：

   ```
   counts = RunCounts { applied: 0, failed: 1, ... }
   issues = [ Issue { code: "PERMISSION_DENIED",
                      message: "无法打开源文件: 拒绝访问。 (os error 5)" } ]
   plan_items = [("keep.txt", …, false), ("move.txt", …, true)]
   ```

   这条输出同时证伪了三个假设，把根因钉死在
   **`open_source_for_rename`（`FILE_SHARE_READ`，不共享写/删）拿不到文件**。

   真因是**环境层**：本机杀软/索引服务对**刚创建的文件**短暂持有排他句柄。
   旁证——**rustc 自己**清理增量编译缓存时也撞了同一个错误：

   ```
   warning: failed to garbage collect finalized incremental compilation session
   directory `...target\debug\incremental\...`: 拒绝访问。 (os error 5)
   ```

   修复落在**测试夹具层**，不在生产代码：`support::write_file` 写完文件后
   调用 `support::settle_fs_noise`，用**与被测代码完全相同的打开模式**
   轮询等待句柄放开（上限 2s，超时如实 panic）。

   两个设计要点：

   - **探测模式必须与失败路径一致。** 第一版用
     `File::options().read(true).open()` 探测——那是共享读写删的默认模式，
     **探测不到**排他锁，等于在等一个根本不会成立的条件。必须用
     `open_source_for_rename` 本身。
   - **挂在夹具上，而不是散在每个用例里。** 上面两个失败点
     （`execute_windows` 的执行、`validate_plan` 的 `write(true)`）
     都源于「刚用夹具建好文件、立刻用」，`write_file` 一处覆盖了全部调用点。

   安全性核对：`busy_source_is_reported_and_not_moved` 是**故意**测
   「文件被占用必须报 `FILE_BUSY`」的用例。它的锁是在 `write_file`
   **返回之后**才由用例自己加上的，而 settle 只在「刚创建完」这一刻探测，
   因此**不会**把这条用例掩盖成通过。

   验证：修复前基线是全量跑 3 次挂 2 次；修复后**连续 8 次全绿**
   （每次 308 通过，且通过数每次一致）。

   > 另有一次全量出现 `rc=101 / passed=0 / 无失败用例名`——那是**构建层**
   > 失败（根本没有测试运行），性质与本次修复的测试层失败不同，
   > 由调试过程中被工具超时 SIGTERM 掉的 cargo 进程留下的 target 目录状态所致，
   > 重跑未再复现。

### 环境备注（本机）

- **所有 `cargo` 命令都要加沙箱豁免**，否则写 `target/` 下的 `.d` / `.fingerprint`
  会被拦成「拒绝访问。(os error 5)」，看起来像杀毒软件锁定。
- 任何 `cargo` 命令前先 `source scripts/msvc-env.sh`。
- Bash 工具缺 `ls` / `head` / `tail` / `mkdir` / `dirname` / `sed` / `uname` / `seq`，
  连 `node_modules/.bin/vitest` 这个 shim 都跑不起来。改用
  `node node_modules/vitest/vitest.mjs run` 直接调用入口；
  输出含 ANSI 颜色码，用 Python 剥掉再读。
- **本机有两处来源都会报 `os error 5`，排查时必须分清**：
  ① **沙箱**拦住写 `target/` 下的 `.d` / `.fingerprint`（解法：cargo 命令加沙箱豁免）；
  ② **杀软/索引服务**对刚创建的文件短暂持有排他句柄（解法：夹具层 `settle_fs_noise`）。
  分不清就会把「自己造成的构建失败」当成「环境噪声」而放过去。
- **长命令（连跑多次测试、批量统计）写成 `.py` 文件再后台跑**，
  直接内联的 Python 一行命令容易被工具超时 SIGTERM 掉；
  而且被 SIGTERM 的 `cargo` 会留下半成品 target 状态，让**下一次**构建失败。
- 判断测试是否真的跑过：看 `test result: ok. N passed` 里的 **N**。
  `rc != 0` 且 `N` 缺失/为 0 时是**构建失败**，不是测试失败——别混为一谈。

### 令牌的四类拒绝（`tests/validate_plan.rs`）

规格要求「伪造或过期 token、修改摘要、重用 token 均必须被后端拒绝」，
每类都有独立测试，且**都绕开界面直接打后端**：

| 测试 | 攻击 | 期望 |
|---|---|---|
| `a_forged_token_is_refused_even_with_the_right_digest` | 拿着正确的 planId / revision / digest 伪造令牌 | `STALE_PLAN` |
| `an_expired_token_is_refused_at_the_exact_boundary` | 恰好到期 | `TOKEN_EXPIRED` |
| `replaying_the_same_token_is_refused` | 重放已消费的令牌 | `TOKEN_USED` |
| `changing_the_digest_after_issue_invalidates_the_token` | 签发后篡改摘要 | `STALE_PLAN` |
| `editing_the_plan_changes_the_digest_so_the_old_token_cannot_be_used` | 端到端：签发 → 编辑 → 用旧令牌 | `STALE_PLAN` |
| `a_token_issued_for_one_plan_cannot_be_used_on_another` | 跨计划挪用 | `STALE_PLAN` |

三类拒绝用了**不同的错误码**（`TOKEN_EXPIRED` / `TOKEN_USED` / `STALE_PLAN`）：
用户能做的事不同（重新校验 / 说明重复提交 / 重新预览），前端不该把它们混成一句话。

### 本轮修掉的问题

1. **`scripts/msvc-env.sh` 依赖 `tail` 与 GNU `sort`**（环境相关但根因在脚本）
   脚本用 `ls | sort -V | tail -n 1` 取版本号。本会话里 `tail` 不存在，
   而 PATH 上的 `sort` 退化成了 Windows 自带的 `sort.exe`（不认 `-V`），
   于是版本号是空串、linker 路径被拼成 `...\MSVC\\bin\Hostx64\x64\link.exe`，
   cargo 报出指向空路径的 `link.exe not found`——极具误导性。
   改成纯 bash 的点分版本比较，并在找不到 linker 时**提前**失败并打印真实路径。

2. **禁用理由只渲染在对话框里**（由 UI 测试暴露）
   确认对话框默认是关的，于是按钮灰着而用户看不到任何原因，只能反复点击去猜。
   修复：把理由移到按钮旁边；并区分「还没校验」与「校验过了但计划又被改了」两种情形。

3. **`Plan` / `ValidationReport` 没进 JSON Schema 的 definitions**
   `get_plan` / `validate_plan` 的返回值拿不到运行时校验，
   前端的 `RESPONSE_CONTRACT` 表也因此缺条目。补齐后 `tsc` 的类型检查才通过。

4. 编译期问题：`PlanBuild` 缺 derive（拿不到 Serialize / 契约生成）、
   `PlanBuild` 的导入路径写错（在 `planner` 而非 `domain::types`）、
   以及 `update_plan` 里「先按 id 查索引、再可变借用同一份 items」的借用冲突
   （改为先解析出位置、让索引的作用域提前结束）。

1. **`cyclic_swaps_are_degraded_instead_of_planned_as_swaps`**

2. **`a_target_created_after_planning_blocks_validation_instead_of_being_renamed`**
   计划生成之后由"竞争方"创建目标，再校验 → 必须报 `TARGET_EXISTS` 且**不自动改名**，
   同时断言那个抢先创建的文件字节没被动过。这是规格 7.1 第 8 条与 E02 的合流点。

3. **`a_failing_migration_rolls_back_and_keeps_the_previous_version`**

### 最有价值的三条测试

1. **`kernel_refuses_to_overwrite_a_target_created_after_the_precheck`**
   打开源句柄（等价于预检查通过）后，由「竞争方」创建目标，再执行重命名 →
   **内核拒绝**，源与目标字节都完好。这验证的是 `ReplaceIfExists = FALSE` 真的生效，
   而不是「我们的预检查运气好」。

2. **`std_fs_rename_would_have_overwritten_the_target`**（对照组）
   同一场景下 `std::fs::rename` 确实会覆盖。没有这条，第 1 条可能只是
   「系统本来就不许覆盖」的错觉。

3. **`detects_source_content_changed_with_identical_size_and_mtime`**
   改写内容后把 mtime 恢复成原值 —— 规格 E01 点名的情况。只有完整内容哈希能检出。

### 本轮修掉的问题（来自用户要求的主动排查）

排查范围：扫描器、IPC 命令层、状态管理。找到两个真问题：

1. **`max_files` 把被跳过的条目也计入额度**（`scanner/walk.rs`）
   规格 6.1 的上限针对的是**普通文件**。原实现用 `entries.len()` 判上限，于是
   一个塞满 `.crdownload` / 隐藏文件 / `.git` 的目录会先把额度吃光，
   真正要整理的文件一条都扫不到。修复：单独维护 `usable_count` 计数器
   （现算会让扫描退化成 O(n²)），并加回归测试
   `skipped_entries_do_not_consume_the_file_limit`。

2. **查询类命令用了语义完全不符的错误码**（`commands.rs`）
   `get_task` 找不到任务时返回 `FILE_BUSY`（「文件被占用」），
   `list_files` 找不到扫描结果时返回 `SOURCE_MISSING`（「源文件不存在」）。
   前端会据此显示误导性提示。修复：两者统一改为 `IpcResult<Option<T>>`，
   与 `choose_root` 一致——**查询不到不是错误，而是「这个 id 在本会话里不存在」**。

另有一处由 `tsc` 抓到的真冗余：按钮只在 `ready|scanned` 时渲染，
`disabled={phase.status === 'scanning'}` 永远不成立。

### T03 完成后的安全复核修复

1. 修复目标祖先 junction 可把文件移到批准根外的问题。移动期间逐级持有目录保护句柄，
   `FILE_FLAG_OPEN_REPARSE_POINT` 保证检查联接本身，并用不共享 DELETE 阻止检查后替换。
2. 修复 `is_reserved_device_name` 对 emoji/中文按字节 `split_at(3)` 导致 panic；同时拒绝
   `COM1 .txt`、`NUL..log` 等 Win32 会归一化为设备名的写法。
3. 完整目标路径的 240 UTF-16 units 上限现在包含批准根；既有源名不再错误套用新名称的 80-unit 限制。
4. 初扫和完整指纹均从单一、不共享写入/删除的句柄采集身份、大小、时间与哈希；卷身份取自句柄并核对。
5. 扫描会跳过多硬链接和离线占位文件；深度超限会同时留下原因并标记 `truncated=true`。
6. Win32 错误码不再被 `io::Error::other` 抹掉；共享冲突稳定返回 `FILE_BUSY`。
7. 前端 IPC 调用链接入生成 Schema 的运行时校验，拒绝畸形信封、错误类型和未知字段；导航切换保持首页工作流挂载。
8. 安全移动逐级查询目录大小写敏感标志；开启该模式时按 v0.1 范围返回不支持。
9. `start_scan` 改为立即返回 taskId，后台枚举；`get_task` 查询终态，`cancel_task` 只发请求，
   扫描线程确认后进入 cancelled，且不保存不完整扫描结果。页面切换后任务与扫描状态继续保留。

## 阻塞与已知限制

- **WebView2 在本沙箱内崩溃**：需要 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--disable-gpu`
  才能渲染。判断是沙箱特有，**未写进项目配置**（ADR-009），待用户在无沙箱终端验证。
- 截图必须用 `scripts/screenshot-window.py --printwindow`：
  禁用 GPU 后 WebView2 走软件渲染，`PrintWindow` 才能拿到画面；
  `SetWindowPos` 的置顶抢不过同样是 TOPMOST 的程序。
- `choose_root` 每次都会往 `roots` 表里新增一条，旧的不会清理。
  当前按「单根工作流」设计（规格 5.2），内存占用很小；
  存储层的 `roots` 表已就绪（T04），会话生命周期清理仍待做。
- **MSVC 组件未登记**（2026-09-17 实测）：`cl.exe`/`link.exe`/头文件/库都在
  `VC\Tools\MSVC\14.44.35207`，但 `vswhere -requires
  Microsoft.VisualStudio.Component.VC.Tools.x86.x64` 无输出。rustc 因此探测不到
  MSVC，退回 PATH 上 Git for Windows 的 `link.exe`（coreutils 硬链接工具）并链接失败。
  **任何 cargo 命令前先 `source scripts/msvc-env.sh`**（T04 新增）。
  这从 T04 起才暴露，因为 `rusqlite` 的 `bundled` 特性第一次需要 C 编译器。
- `pnpm contracts:check` 在本机失败：`pnpm → cmd → powershell → cargo` 把非 ASCII
  项目路径按 GBK 解码。等价校验（重新生成 + 哈希比对）通过，详见 T04 一节。
- **本机 bash 的 coreutils 状态会在会话之间变化**（T11 实测）：
  T04 时记录为「`ls`/`sort`/`head`/`tail`/`sed` 实测正常」，而 2026-09-21
  实测又**全部** `command not found`（exit 127，连 `dirname` 都没有）。
  结论：**不要依赖 bash 里存在 coreutils**——列目录用 Glob、读文件用 Read、
  取时间与文本处理用托管 Python
  （`...\python\versions\3.13.12\python.exe -c ...`），
  命令输出统一 `> 项目内/tmp/x.txt 2>&1` 再 Read。
- `cmd.exe` 与 `powershell` 从 bash 调用被安全策略拦截；工具的 PowerShell 通道
  同样会拦 `Add-Type`（T11 想用 `System.Drawing` 渲染中文测试图时被拦）。
  要生成图片时改用托管 venv 里的 Pillow（见下一条）。
- **托管 Python venv 已装 Pillow**（T11 新增）：路径形如
  `<用户目录>\.workbuddy\binaries\python\envs\default\Scripts\python.exe`
  （发布物里不写真实用户路径，见 `docs/TEST_MATRIX.md` 8.5 的内容扫描）。
  T11 的 OCR 中文图夹具由它生成，脚本留在 `tmp/make_ocr_fixture.py`。
- **自造 PNG 必须补齐 IDAT 与 IEND**（T11 实测）：只给签名 + IHDR
  会被解析器判成「这不是一张图」（PIL 报 `UnidentifiedImageError`），
  于是「测像素上限」的用例会先撞上「文件损坏」，测不到目标分支。
